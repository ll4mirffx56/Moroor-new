# مرور V2 | Moroor V2 — سیستم مدیریت مطالعه و تحلیل یادگیری

داشبورد فارسی و راست‌چین برای برنامه‌ریزی مطالعه، مرور فاصله‌دار، ثبت آزمون، پیگیری دوره‌ها، بدهی مطالعاتی، گزارش‌های واقعی و یادداشت‌ها. رابط کاربری با سبک Glass و تم تاریک، تقویم شمسی و نمودارهای سبک بدون وابستگی به کتابخانهٔ نمودار ساخته شده است.

## بخش‌های برنامه

1. **داشبورد** — کارت‌های مطالعهٔ امروز، هدف مطالعه، مرورها، عملکرد آزمونی، دوره‌ها و بدهی مطالعاتی؛ نمودارهای روند، توزیع دروس، مرورهای پیش‌رو، وضعیت دوره‌ها و فعالیت. کارت‌ها قابل جابه‌جایی و پنهان‌سازی هستند.
2. **برنامه و مرور** — سلسله‌مراتب درس ← فصل ← موضوع، ساخت مرور با تقویم شمسی و فاصله‌های پیشنهادی ضعیف/متوسط/خوب/عالی (۱/۲/۴/۷ روز، قابل تنظیم)، وضعیت‌های در انتظار/انجام‌شده/عقب‌افتاده/زمان‌بندی‌شده و بدهی مطالعاتی با اولویت و وابستگی.
3. **عملکرد آزمونی** — ثبت عملکرد روزانه چنددرسی، آزمون‌های چنددرسی، فرمول `((correct × 3) − wrong) / (total × 3) × 100`، میانگین‌های ۷/۳۰/۹۰ روزه، مقایسهٔ دروس و موضوعات و نمودارهای تعاملی.
4. **دوره‌های آموزشی** — دو شاخص مستقل پیشرفت ویدئو و پیشرفت وزنی مراحل یادگیری (ویدئو، آزمون، تمرین، مرور، تسلط) با وزن قابل تنظیم، مدیریت جلسات و ساعت‌ها.
5. **گزارش‌ها** — گزارش هفتگی/ماهانهٔ واقعی، مقایسهٔ هفته به هفته، مرور هفتگی (نقاط قوت، مسئله، بیشترین پیشرفت/افت، کارهای ناتمام، پیشنهادها) و تقویم فعالیت به سبک GitHub سازگار با تاریخ شمسی. بدون دادهٔ کافی، نتیجه‌گیری تحلیلی انجام نمی‌شود.
6. **یادداشت و تنظیمات** — یادداشت متصل به درس/فصل/موضوع/دوره/آزمون با جست‌وجو و ویرایش، اهداف مطالعه، فاصله‌های مرور، وزن مراحل دوره، دسته‌بندی کارت‌ها، پشتیبان‌گیری JSON/Excel و ورود غیرمخرب داده.

## قواعد محاسباتی

- **پاسخ نزده** = `total − correct − wrong`؛ فقط اعداد صحیح نامنفی پذیرفته می‌شوند و `correct + wrong` نباید از `total` بیشتر باشد.
- پاسخ نزده نمرهٔ منفی ندارد؛ درصد آزمون از مجموع پاسخ‌ها محاسبه می‌شود، نه میانگین درصد درس‌ها.
- اگر `total = 0` باشد درصد به‌جای صفر گمراه‌کننده، «نامشخص» است.
- تاریخ‌ها در داده به‌صورت ISO میلادی ذخیره و فقط در لایهٔ نمایش به شمسی تبدیل می‌شوند؛ هفتهٔ ایرانی از شنبه شروع می‌شود و «امروز» بر مبنای تهران است. سال ۱۴۰۵ هرگز با جداکنندهٔ هزارگان نمایش داده نمی‌شود.

## داده و همگام‌سازی

داده‌های هر حساب در یک سند JSON نسخه‌دار (`schemaVersion: 2`) در جدول `public.user_app_state` نگهداری می‌شود. این معماری از نسخهٔ قبلی حفظ شده و آن را به مجموعه‌های نرمال‌شده درون سند گسترش داده است:

- خواندن/نوشتن با RLS و `auth.uid() = user_id` محدود به مالک است.
- ذخیره با compare-and-swap اتمیک (`save_user_app_state`) انجام می‌شود؛ در تعارض، تغییرات رکوردهای مستقل ادغام و سپس دوباره تلاش می‌شود.
- تغییرات دستگاه‌های دیگر از طریق Supabase Realtime دریافت می‌شوند؛ وضعیت همگام‌سازی و زمان آخرین همگام‌سازی نمایش داده می‌شود.
- داده‌های نسخهٔ ۱ (مرورها، عملکرد روزانه، تنظیمات و ترتیب کارت‌ها) هنگام بارگذاری به‌صورت خودکار و بدون حذف به ساختار ۲ منتقل می‌شوند. کلیدهای قدیمی `localStorage` نیز یک‌بار منتقل می‌شوند.
- ورود فایل پشتیبان ادغامی است و رکوردهای موجود را حذف نمی‌کند؛ پیش‌نمایش و تأیید پیش از اعمال لازم است.

بدون متغیرهای Supabase، برنامه در «حالت محلی» کاملاً قابل استفاده است و این وضعیت را در نوار بالای صفحه اعلام می‌کند. ورود و همگام‌سازی ابری فقط با تنظیم متغیرها فعال می‌شوند.

## اجرا

نیازمند Node.js 20+ و npm:

```bash
npm install
npm test
npm run build
npm run dev
```

## آزمون‌ها

`npm test` ابتدا ماژول‌های خالص `src/lib` را با TypeScript کامپایل و سپس ۲۶ آزمون واحد/یکپارچه را با `node:test` اجرا می‌کند. پوشش شامل محاسبهٔ درصد آزمون و نمرهٔ منفی، پاسخ نزده و اعتبارسنجی ورودی، تبدیل و قالب‌بندی شمسی (از جمله سال ۱۴۰۵)، هفتهٔ شنبه‌محور، فاصله‌های مرور، اهداف، پیشرفت دوره، مرتب‌سازی بدهی، گزارش هفتگی/ماهانه، آستانهٔ کفایت داده، دستاوردها، مهاجرت سند نسخهٔ ۱ و ۲، مقاومت در برابر دادهٔ خراب، پشتیبان‌گیری و ادغام غیرمخرب، و ادغام سه‌طرفهٔ همگام‌سازی است.

آزمون‌های واقعی Supabase (ورود، RLS، Realtime و همگام‌سازی دو دستگاه) بدون پروژه و اعتبارنامهٔ Supabase اجرا نشده‌اند؛ برای اجرای آن‌ها `.env.local` را طبق `.env.example` بساز و migrationها را اعمال کن.

## راه‌اندازی Supabase

1. سه migration موجود در `supabase/migrations/` را به ترتیب در SQL Editor اجرا کن (idempotent و غیرمخرب).
2. `.env.example` را به `.env.local` کپی کن و `VITE_SUPABASE_URL` و `VITE_SUPABASE_PUBLISHABLE_KEY` را مقدار بده. هرگز `service_role` یا Secret key را در فرانت‌اند نگذار.
3. در GitHub → Settings → Secrets and variables → Actions → Variables همان دو متغیر را برای Build بساز.
4. در Supabase → Authentication، ورود ایمیل/رمز را فعال و Site URL/Redirect URLs را با آدرس سایت تنظیم کن.

جزئیات بیشتر در `CLOUD-SETUP.md`.

## انتشار

Workflow موجود در `.github/workflows/deploy.yml` روی `main` و `v2-dev` تست و Build می‌کند، اما مرحلهٔ Deploy فقط برای `main` اجرا می‌شود. مسیر پایهٔ GitHub Pages برای مخزن پروژه به‌صورت خودکار در `vite.config.ts` تعیین می‌شود و مسیریابی برنامه hash-based است، بنابراین Refresh روی بخش‌های مختلف صفحهٔ 404 تولید نمی‌کند. توسعه و بررسی تغییرات باید در `v2-dev` انجام شود و انتشار Production تنها با اجازهٔ صریح صورت گیرد.
